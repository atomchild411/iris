# The R4600 — expectations without an oracle

The suite selects its expectations by `PRId`. The R4400 and the R5000 have both
run it on real Indys and pass every check (`oracle/`); **no R4600 has**. This
file says where each R4600 answer comes from, so that a failure on an R4600 can
be weighed properly and so that the first real R4600 run knows what it is
confirming.

The reason the case exists at all is the `sgiindy_MiSTer` FPGA core, which
presents itself as an R4600 (PRId/FIR `0x2020`): IRIX 5.3 hard-codes a 32-byte
data-cache line for imp 0x20 and a 16-byte one for the R4400, so that core
cannot pose as an R4400. Before this case existed, `identify()` refused imp 0x20
with rc=127.

## Where each expectation comes from

| class | tests | source |
|---|---|---|
| **Documented** | `identity/prid` (imp 0x20), `identity/fir` (imp 0x20), `identity/cache_geometry` and `cache/geometry` (16 KB I and D, 32-byte lines), `cache/set_conflict` (two ways), `identity/tlb_size` (48) | IDT79R4600 data sheet; IRIX's `hinv` names an Indy R4600's FPU from FIR imp 0x20 |
| **Both oracles agree** | every test registered `CPU_ALL` with no CPU branch — including the NaN rules (`fpu/snan_operands`, `fpu/compare_nan`, `fpu/cmp_*`), `excep/cop2_unusable` with CU2 set, `fpu/vec_cvt_from_l` past 2^53, the trap and Cause rules | an R4400 rev 6.0 and an R5000 rev 1.0 give the same answer, so an R4600 is held to it |
| **Both oracles agree, one of them reported** | the `fpu/denorm_*` group and `fpu/qnan_operand` | asserted on the R4400; *reported* on the R5000, and the R5000's reported lines (`oracle/r5000-rev1.0-run2-clean.log`) are byte-identical to what the R4400 asserts, case by case. The R4600 is asserted with the R4400 |
| **ISA level** | `mips4/*` refusals: Reserved Instruction for SPECIAL / REGIMM / COP1X encodings, Unimplemented Operation (`EXC_FPE`) for COP1 function codes | the R4600 is a MIPS III part like the R4400. The FPE-not-RI rule for COP1 was measured on the R4400 only |
| **Unknown — either measured answer passes** | `mem/lwr_all_offsets`, partial loads (offsets 0-2) | the R4400 keeps the upper half of `rt`, the R5000 sign-extends. The R4600's integer unit is QED's, like the R5000's, but that is not a measurement. The log names which behaviour it saw; any third answer fails |
| **Reported, as on the R4400** | `mips4/multi_fp_cc` (`c.eq.s` with cc != 0) | not a defined MIPS III encoding |

## What the suite does not cover on an R4600

Things a real R4600 differs in that no test here looks at, so a pass says
nothing about them:

- **No Watch registers** (WatchLo/WatchHi, the Watch exception), no secondary
  cache (Config.SC = 1) and so no cache-error or VCE exceptions.
- **The cache organisation beyond correctness.** `cache/set_conflict` checks
  that a set conflict never returns the wrong line, not how many ways hold a
  line. A direct-mapped cache that reports R4600 geometry passes — which is
  exactly what the `sgiindy_MiSTer` core has.
- Anything about `Config.EC` / the clock ratio, which the PROM reads per CPU
  family.

## The first R4600 run

When an R4600 Indy runs this, the useful outcomes are, in order:

1. `mem/lwr_all_offsets` — the log line says which answer the part gives; gate
   it the way the R5000 forced (`mem.c`) and delete the "either" branch.
2. Any failure in the "both oracles agree" classes would be the interesting
   one: an R4600 that differs from both its predecessor and its successor.
3. `mips4/recip_rsqrt*` and `mips4/fp_cond_move_*` confirm (or not) that the
   R4600's FPU, like the R4400's, raises Unimplemented Operation for COP1
   function codes it lacks.

Record the log under `oracle/` and move the confirmed rows of the table above
into the "measured" column the way `docs/findings.md` did for the R4400.
